# ТЗ для незалежної перевірки (Codex): «Стежка» / plast-hike-planner

## 1. Твоя роль і правила
Ти — незалежний рецензент. Автор проєкту — Назар, нетехнічний провідник Пласту. Код писав разом з іншим ШІ-асистентом. Тобі треба **перевірити, чи все працює так, як заявлено**, і знайти, де ні. Перевіряй на ділі: запускай команди й тести, читай код. Чужим висновкам на слово не вір, зокрема коментарям і документації в репозиторії.

**Правила:**
- **Нічого не змінюй** у коді, даних і документації. Єдиний файл, який ти створюєш, — звіт (розділ 8).
- Працюй на гілці **`web`**: там усе. Гілка `main` — це лабораторна без вебу (5 комітів позаду).
- Ключів немає й не буде: ні OpenRouter, ні Obsidian. Моделей не викликай. Для агента є тести з тренувальною моделлю (`FakeLLM`) і тренувальним Obsidian (`FakeObsidian`) поверх **справжнього** сервера plast-trail у пам'яті.
- Не запускай Ollama й не завантажуй моделей.
- Мережа потрібна лише для `uv sync`. Погода в тестах іде з записаних відповідей (`WEATHER_MODE=replay`). Не роби запитів до Open-Meteo чи OpenStreetMap.
- Не відкривай і не створюй `.env`. Не роби комітів і не пуш.

## 2. Що це за проєкт
Лабораторна «MCP Integration» (KSE Agentic AI School). Дедлайн 27.11.2026, захист наживо 10–15 хв. На захисті **не можна користуватися ШІ**, тому автор має вміти пояснити кожен рядок.

Агент планує пластові мандрівки Карпатами:
- читає запит провідника (нотатку Obsidian або діалог);
- знаходить маршрут, перевіряє норми безпеки, погоду й запаси;
- записує план назад в Obsidian.

Два MCP-з'єднання:
- **Obsidian** — існуючий сервер, плагін Local REST API з вбудованим MCP-ендпоінтом, 20 інструментів;
- **plast-trail** — власний сервер FastMCP, окремий процес, streamable HTTP на `127.0.0.1:8770/mcp`. Має 6 інструментів:
  - `find_routes`;
  - `resolve_places`;
  - `validate_hike_plan`;
  - `assess_weather_risk`;
  - `calculate_supplies`;
  - `get_route_profile`.

Агент — це граф LangGraph. Код задає порядок кроків, модель думає всередині кроків. Модель — OpenRouter (безкоштовна) з переходом на локальну Ollama.

Веб (гілка `web`, бонус до захисту) запускається командою `uv run plast-web` і складається з трьох частин:
- чат з тим самим агентом;
- сторінки збережених планів;
- одна межа `present()`, яка перетворює дані агента на людський український текст.

**Що прочитати насамперед:**
- `README.md`;
- `docs/design-rationale.md`;
- `docs/tool-contracts.md`;
- `docs/demo-script.md`;
- `docs/manual-tests.md`;
- `data/rules.yaml` (норми безпеки);
- `research/plast-norms-research.md` (джерела норм);
- код у `src/plast_trail/`, `src/plast_agent/`, `src/plast_web/`;
- тести в `tests/`.

## 3. Вимоги лабораторної (з умови завдання, скорочено)
**Мінімальні умови.** Якщо порушено бодай одну, оцінка не вища за 59/100:
- щонайменше 3 **змістовні** власні інструменти;
- є інструмент доступу до первинного джерела даних;
- обидва MCP-з'єднання успішно викликаються;
- агент використовує **обидва** сервери у своїх потоках.

**Змістовний інструмент:**
- має доменну мету;
- робить реальну обробку (правила, обчислення, перевірку, планування), а не просто повертає збережений текст;
- має спроєктований контракт, а не довільний рядок чи словник;
- має окрему відповідальність;
- його результат видно в роботі агента.

Щонайменше 2 з 3 мають бути **не** пошуком. Пошук може зарахуватися як один.

**Part A (існуючий сервер):**
- налаштований;
- інструмент знайдено й викликано;
- результат впливає на подальший крок;
- контракт пояснено (назва, опис, аргументи, результат, помилки, побічні ефекти);
- на захисті показано реалістичну відмову: сервер недоступний, неправильний ключ або нотатки немає.

**Part B (власний сервер):**
- окремий процес, запускається незалежно;
- явні схеми входу й виходу для кожного інструмента;
- публічне API без авторизації або локальний чи завантажений набір даних;
- помилки відрізняються від успішного порожнього результату.

**Part C (документація контрактів):** для кожного власного інструмента потрібні назва, призначення, точний опис для моделі, схема входу (типи, обов'язковість, обмеження, типові значення), схема виходу, помилки, побічні ефекти й приклад. Також треба описати Obsidian і хоча б один його інструмент.

**Part D (експлуатація):**
- жодних секретів у репозиторії;
- конфігурація через змінні середовища;
- дотримання лімітів API;
- для мережевого API — записані **справжні** відповіді й режим відтворення, що йде **тим самим шляхом розбору**, а не «гілка з готовою відповіддю»;
- усе потрібне для відтворення лежить у репозиторії.

**Здача:**
- README з передумовами, встановленням, конфігурацією й окремими командами запуску агента та сервера;
- контракти;
- фікстури й інструкція відтворення;
- обґрунтування рішень: роль існуючого сервера; чому кожен інструмент стоїть на межі MCP; компроміси й обмеження;
- сценарій захисту.

**Рубрика (100):**
- архітектура й протокол — 25;
- документація й обґрунтування — 25;
- дизайн інструментів і схем — 18;
- інтеграція в потік агента — 14;
- існуючий сервер і демонстрація відмови — 10;
- надійність і відповідальний доступ до даних — 8.

## 4. Що ми хочемо мати (критерії приймання)
Для кожного пункту дай висновок: **виконано / частково / ні**, з доказом.

**A. Лабораторна (CLI + Obsidian, основна для захисту)**
1. `uv run plast-trail` запускає сервер окремим процесом. Лог показує кількість маршрутів, статус норм і режим погоди.
2. `uv run plast-agent "<нотатка>"` і `uv run plast-agent --chat`. Агент:
   - підключається до обох серверів (`initialize` + `tools/list`);
   - читає запит з Obsidian;
   - шукає маршрути, пропонує план, перевіряє його, дивиться погоду, перепропонує за потреби;
   - рахує запаси й профіль;
   - пише план, малюнок SVG і трек GPX в Obsidian;
   - дописує рядок статусу в нотатку-запит.
3. Результат Obsidian (текст запиту) справді визначає подальші кроки.
4. Відмови пояснено людською мовою, без падіння зі стеком:
   - Obsidian закритий;
   - неправильний ключ;
   - нотатки немає;
   - plast-trail не запущений;
   - модель недоступна або вичерпано ліміт (429).
5. Режим `replay` відтворює записані відповіді Open-Meteo через той самий розбір, що й `live`.

**B. Сервер plast-trail**
6. Шість інструментів, у кожного схема входу й виходу (Pydantic), з обмеженнями (enum, межі чисел, `extra="forbid"`).
7. Помилки мають структуру `{error: {code, message, hint}}` з `isError`. Порожній результат — успіх (`routes: []` з поясненням), а не помилка.
8. Правила з `data/rules.yaml` застосовуються правильно:
   - `severity: error` робить план невалідним, `warning` лише попереджає;
   - `value: null` означає, що норми немає, тож число показується, але не оцінюється.

**C. Агент**
9. Розуміння запиту:
   - модель читає текст один раз;
   - код перевіряє й виправляє (`understanding.refine`);
   - назви місць перевіряє довідник `resolve_places`;
   - вигадані моделлю значення відкидаються.
10. Цикл «пропозиція → перевірка → погода»:
    - не більше 4 спроб;
    - повтор відхиленого плану забороняється;
    - після погоди з високим ризиком агент змінює дату або маршрут;
    - якщо спроби вичерпано, лишається найкращий валідний план, а не провал.
11. Статуси плану: `ok`, `attention`, `risky`, `group`, `failed`. `group` означає, що маршрут підходить, але бракує дорослих. Це порада, а не вирок, і це свідоме рішення автора.
12. Без ключа OpenRouter агент працює лише на локальній моделі. Без жодної моделі — зрозуміле повідомлення.

**D. Плани**
13. Нотатка Obsidian, SVG, GPX і посилання Mapy.com узгоджені з результатами інструментів. Жодне число не вигадано в рендері.
14. Кожен прогін зберігає план у `out/plans/<id>.json` (`plan_store.py`). Id безпечні для URL і шляхів.

**E. Веб (гілка `web`)**
15. `uv run plast-web`:
    - слухає лише `127.0.0.1`;
    - відмовляє чужим `Host` і `Origin`, зокрема для WebSocket;
    - віддає суворий CSP;
    - сторінка вставляє дані лише як текст (жодного `innerHTML` з даними);
    - Leaflet підключено з cdnjs з SRI.
16. Межа `present()` (`src/plast_web/view.py`): на сторінку не потрапляють id маршрутів і точок (`r8613349`, `w30`), коди (`ENDS_ON_TOP`), теги джерел `[S13]`, ключі районів (`chornohora`) й англійський текст інструментів. Висновок плану пише код із результатів інструментів (модель його не пише).
17. Чат (`conversation.py`):
    - питає те, чого бракує, з кнопками швидкої відповіді (відповіді читає код);
    - картку «Ось що я зрозумів» можна правити без виклику моделі;
    - прогрес іде через `astream`;
    - картка плану веде на сторінку плану;
    - повідомлення після плану змінює цей план;
    - «6-7» читається як 7;
    - розмова живе на сервері: після перезавантаження вкладки відновлюється, закриття вкладки не зупиняє планування;
    - одночасно складається лише один план.
18. `runtime.py`:
    - одна задача-наглядач на кожен MCP-сервер, з перепідключенням;
    - якщо порт plast-trail вільний, plast-web запускає сервер сам (`sys.executable -m plast_trail.server`) і зупиняє його при виході;
    - чужий запущений сервер не чіпає.
19. `cli.plan_and_write` отримав необов'язкові `prepared`, `on_node`, `report`, `trace_from`. Поведінка CLI без них **не змінилася**.

**F. Переносимість**
20. Проєкт працює на Windows, Linux, Intel Mac і Apple silicon. Залежності:
    - `tzdata`;
    - `cryptography<49` (є готові збірки для Intel Mac);
    - `starlette` і `uvicorn` оголошено явно.
21. Вивід і запис файлів у UTF-8, також на консолі cp1252. CI (`.github/workflows/ci.yml`) на 4 системах.
22. Свіжий клон без `.env` проходить `uv sync --locked` і `uv run pytest -q`.

**G. Норми**
23. `data/rules.yaml` затверджено автором для проєкту 16.11.2026 (`status: approved`, у кожного запису `approved: true`). Перевір:
    - сервер і плани показують статус затвердження;
    - слово «чернетка» лишається лише там, де статус DRAFT;
    - шапка файла чесно каже, що це не рішення Пласту.

**H. Документація**
24. README, контракти, обґрунтування, сценарій захисту й ручні тести відповідають коду: кількість інструментів, тестів, команди, назви, порти, поведінка. Знайди кожну розбіжність.

## 5. Відомі рішення й обмеження (не звітуй як баги, але скажи, якщо обґрунтування слабке)
- Захист: CLI + Obsidian. Веб — бонус, лежить у гілці `web`.
- Записана погода покриває лише 14–29.11.2026. Поза цим вікном план складається з позначкою «прогнозу ще немає».
- Маршрути в даних — в один бік. Якщо маршрут закінчується на вершині, сервер попереджає (`ENDS_ON_TOP`).
- Для чату потрібен відкритий Obsidian. Без нього працюють лише сторінки планів.
- Веб для інших людей (онлайн) ще не робили: зараз він лише локальний.
- Норми затверджено для проєкту, а не Пластом. Питання рівня Пласту відкриті (`research/plast-norms-research.md`, розділ 5).
- Діалог у вебі (`conversation.py`) свідомо повторює логіку `chat.py`, щоб не чіпати CLI перед захистом.
- `docs/web/mockup*` — статичний макет, не частина продукту (і не закомічений).

## 6. Як запускати
```bash
uv sync --locked
uv run pytest -q
uv run plast-trail --port 8799
PLAST_TRAIL_URL=http://127.0.0.1:8799/mcp uv run python scripts/smoke_server.py
uv run plast-web --port 8790 --no-browser
```
- `uv run pytest -q`: очікується 183 passed (або більше), без мережі.
- `uv run plast-trail --port 8799`: окремий процес, `WEATHER_MODE=replay` за замовчуванням.
- `smoke_server.py` (у другому терміналі): усі 6 інструментів, помилки, порожній результат.
- `uv run plast-web`: без `.env` чат вимкнений, сторінки планів працюють.

Щоб побачити план на сторінці без моделі, згенеруй записи так, як це роблять `tests/test_web.py::record_for` і `tests/test_chat.py::talk`, у тимчасову папку (`PLAST_PLANS_DIR`). Чат цілком перевіряється в `tests/test_chat.py`.

## 7. На що звернути особливу увагу (найдорожчі помилки)
1. **Безпека дітей.** Чи може план, що порушує норму з `severity: error`, дістати статус `ok` або `attention`? Чи правильно рахуються км, набір висоти, час приходу, співвідношення дорослих і вага наплічника? Чи є межові випадки (0 дорослих, 1 день, найдовший маршрут, новацтво й ночівля не в хатині), де перевірка мовчить?
2. **Мінімальні умови рубрики** (розділ 3). Чи справді кожен з 6 інструментів змістовний і окремий? Чи могла б комісія сказати, що якийсь лише «повертає дані»?
3. **Відтворення погоди.** Чи `replay` справді йде тим самим розбором, що й `live`?
4. **Збій на живому захисті.** Що може зламатися на іншому ноутбуці чи в аудиторії: порти, сертифікат Obsidian, час, часовий пояс, кирилиця в шляхах?
5. **Веб:**
   - XSS через назви з OSM або текст моделі (зокрема SVG `route.svg`, підказки Leaflet, посилання `obsidian://`);
   - обхід перевірки `Host`/`Origin`;
   - витоки технічного тексту, які детектор `looks_technical` пропускає.
6. **Паралельність:**
   - спільна MCP-сесія з кількома розмовами;
   - скасування;
   - перепідключення після падіння сервера;
   - дочірній процес, що лишився сиротою (особливо на Windows).
7. **Тести.** Чи перевіряють вони поведінку, чи лише те, що код виконується? Яких важливих тестів бракує?
8. **Зрозумілість для захисту.** Які місця коду автору буде найважче пояснити без ШІ? Що можна спростити без втрати функцій?
