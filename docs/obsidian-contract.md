# Obsidian MCP: the existing server and the tools this project uses

Generated by `scripts/gen_docs.py` from the live server on 2026-11-14. Descriptions and input schemas are copied from `tools/list`; outputs are real calls against the demo vault.

## Connection (this project's configuration)

- **Server:** `obsidian-local-rest-api` 1.0.0, built into the Obsidian community plugin **Local REST API with MCP** by Adam Coddington (approved project `coddingtonbear/obsidian-local-rest-api`), tested with plugin 5.5.2 and Obsidian 1.15.1.
- **Transport:** streamable HTTP at `https://127.0.0.1:27124/mcp/` over TLS with the plugin's self-signed certificate (verified against `certs/obsidian-local-rest-api.crt`, not disabled).
- **Auth:** `Authorization: Bearer <OBSIDIAN_API_KEY>` from `.env` (git-ignored).
- **Vault:** a dedicated `demo-vault/` with fictional data only (`Запити/` requests, `Плани/` output). The plugin exposes only the vault that is open, never the personal one.
- **Discovered tools (20):** `vault_list`, `vault_read`, `vault_write`, `vault_read_binary`, `vault_append`, `vault_patch`, `vault_delete`, `vault_move`, `vault_copy`, `vault_get_document_map`, `active_file_get_path`, `search_query`, `search_simple`, `tag_list`, `command_list`, `command_execute`, `open_file`, `vault_get_download_url`, `vault_get_upload_url`, `events_get_listener_url`. The agent uses 4 of them.

## Why this server has a role in the project

A Plast leader already keeps notes; Obsidian is where the request is written in plain words and where the finished plan has to land, next to the request, readable and editable by people. The agent therefore starts by reading a human-written note (input), and ends by writing a human-readable plan and a link back (output). Both ends are real effects on an external environment, and the content read from Obsidian (group, dates, limits like «не більше 12 км на день») directly changes the later tool calls: the group limits are passed to `validate_hike_plan` and override the rules when stricter.

## `vault_read`

| Contract element | Content |
|---|---|
| Role in this project | Step 1 of every run: reads the leader's request note (free text) that the model then parses. Its content is the agent's main input; without it the run stops. |
| Error conditions | Missing note → `isError: true`, text `File not found: <path>`; the agent then calls vault_list and tells the person which requests exist. Wrong key → HTTP 401 at connect; Obsidian closed → connection refused. |
| Side effects | None (read-only). |

**Model-facing description (exact):**

> Read a vault file's content and metadata. Returns a JSON object with: content (full markdown text), path, tags (array of tag strings), frontmatter (parsed YAML front-matter as an object), stat ({ctime, mtime, size}), links (array of vault-relative paths this file links to), backlinks (array of vault-relative paths of files that link here), unresolvedLinks (array of link text in this file that does not resolve to an existing vault file), and version (the file's version token -- pass it back as ifMatch to vault_write, vault_append, vault_patch, vault_delete, vault_move or vault_copy so that write fails, rather than overwriting someone else's change, if the file has changed in between). Throws if the file does not exist. The three link fields reflect Obsidian's metadata cache as it stands and may be incomplete while Obsidian is still indexing the vault after startup; the server-status resource (obsidian://local-rest-api/status) reports, under state.metadataCache, when the plugin last heard the cache resolve and when it last heard any indexing activity.  When targetType and target are both provided, returns only the matched section as a plain string (markdown) or JSON value (frontmatter) instead of the full object. To save context, call vault_get_document_map first to identify headings, block IDs, or frontmatter keys, and prefer targeted reads over full reads for anything but short files.  This tool reads text. A file whose bytes are not valid UTF-8 — an image, a PDF, any attachment — is refused rather than returned as the lossy string decoding it would produce; read those with vault_read_binary instead.

**Input schema**

| Field | Type | Required | Constraints | Default | Description |
|---|---|---|---|---|---|
| `path` | string | yes | — | — | File path relative to vault root |
| `targetType` | enum: `heading` / `block` / `frontmatter` | no | — | — | Type of section to extract: 'heading', 'block' reference, or 'frontmatter' key |
| `target` | array of string \| string | no | — | — | Section to extract. For a heading: an array of heading texts naming the path from the top level down to the target (e.g. ["Heading 1","Subheading"]) — a bare string is rejected, even for a single top-level heading. If a heading is a duplicate of an earlier sibling, its map key carries an extra non-printable marker suffix; copy that key verbatim from vault_get_document_map, don't retype it. For a block: the bare block id without '^' — likewise, a duplicate block id's later occurrence carries the same kind of marker suffix in vault_get_document_map's blocks list. For a frontmatter field: the key name. Use vault_get_document_map to discover valid heading paths and block ids. |
| `scope` | enum: `content` / `marker` / `markerAndContent` | no | — | — | Which part of the target to read (default 'content'), mirroring vault_patch's scopes: what a scope returns is exactly what a 'replace' at that scope consumes. 'content': the node's body — a heading's body with levels made relative to it, a block's text, a frontmatter value. 'marker': the label — a heading's raw text (no '#'s, no duplicate-marker suffix), a block's bare id, a frontmatter key. 'markerAndContent': the whole node — a heading's subtree with its own line as '# Title' (levels relative to its parent), a block's full span including its '^id', a frontmatter entry as a {key: value} object. Requires targetType and target. |

**Output:** no `outputSchema`; a text block containing JSON.

**Example input**

```json
{
  "path": "Запити/Мандрівка гуртка Сокіл.md"
}
```

**Example output** (real call)

```json
{
  "tags": [],
  "frontmatter": {},
  "stat": {
    "ctime": 1794688627436,
    "mtime": 1794692914852,
    "size": 1069
  },
  "path": "Запити/Мандрівка гуртка Сокіл.md",
  "content": "# Мандрівка гуртка «Сокіл»\n\nХочемо зробити мандрівку для гуртка в Карпатах. Це демо-запит, усі дані вигадані.\n\n- **Група:** юнацтво, 10 юнаків і юначок (13–15 років) і 2 дорослі виховники.\n- **Коли:** виходимо в суботу, 21 листопада 2026, на 3 дні. ## `vault_list`
```

| Contract element | Content |
|---|---|
| Role in this project | Recovery path: when the requested note is missing, the agent lists `Запити/` to show what exists; also `plast-agent --list`. |

**Input schema**

| Field | Type | Required | Constraints | Default | Description |

## `vault_write`

| Contract element | Content |
|---|---|
| Role in this project | Final step: writes the finished plan note to `Плани/<request> — план.md` (route table, weather, supplies, documents checklist, the agent's decision log). |
| Error conditions | Obsidian unreachable at write time → the agent saves the note to `out/` locally and reports it. Binary extensions or NUL bytes are refused by the plugin. |
| Side effects | **Creates or overwrites** a file in the vault (parent folders created). The agent writes only under `Плани/`. |

**Model-facing description (exact):**

> Create or overwrite a vault file with the given content. Text only: a path whose extension names an image, audio, video, font, PDF or archive type is refused, as is content containing a NUL byte, because writing text there would corrupt the file -- upload those bytes with vault_get_upload_url, or PUT /vault/<path> over the REST API. Creates any missing parent directories automatically. Overwrites without warning if the file already exists, unless you pass ifMatch (overwrite only the version you read) or ifNoneMatch '*' (create only). Returns the written file's new version token.

**Input schema**

| Field | Type | Required | Constraints | Default | Description |
|---|---|---|---|---|---|
| `path` | string | yes | — | — | File path relative to vault root |
| `content` | string | yes | — | — | Full file content (markdown text) |
| `ifMatch` | string | no | — | — | Make this call conditional on the file being unchanged: pass the version token from vault_read's or vault_get_document_map's 'version', or from the 'version' a previous write returned. If the file has changed since, or no longer exists, the call fails and nothing is written -- read the file again and redo your edit against what is there now. '*' instead means "only if the file exists". |
| `ifNoneMatch` | string | no | — | — | Pass '*' to make this call create-only: it fails, writing nothing, if the file already exists. |

**Output:** no `outputSchema`; a text block containing JSON.

**Example input**

```json
{
  "path": "Плани/Мандрівка гуртка Сокіл — план.md",
  "content": "(the full plan note; this example re-writes the existing note unchanged)"
}
```

**Example output** (real call)

```json
{
  "message": "OK",
  "version": "515a7f"
}
```

## `vault_append`

| Contract element | Content |
|---|---|
| Role in this project | After writing the plan, appends one status line with a wiki-link to the plan into the request note, so the leader sees the result where they wrote the request. |
| Error conditions | Same as vault_write. |
| Side effects | **Appends** text to an existing note (creates it if missing). |

**Model-facing description (exact):**

> Append content to the end of a vault file. Creates the file if it does not already exist. Text only, on the same terms as vault_write: a path whose extension names a binary type is refused, as is content containing a NUL byte. ifMatch and ifNoneMatch make the append conditional, as for vault_write. Returns the file's new version token.

**Input schema**

| Field | Type | Required | Constraints | Default | Description |
|---|---|---|---|---|---|
| `path` | string | yes | — | — | File path relative to vault root |
| `content` | string | yes | — | — | Content to append |
| `ifMatch` | string | no | — | — | Make this call conditional on the file being unchanged: pass the version token from vault_read's or vault_get_document_map's 'version', or from the 'version' a previous write returned. If the file has changed since, or no longer exists, the call fails and nothing is written -- read the file again and redo your edit against what is there now. '*' instead means "only if the file exists". |
| `ifNoneMatch` | string | no | — | — | Pass '*' to make this call create-only: it fails, writing nothing, if the file already exists. |

**Output:** no `outputSchema`; a text block containing JSON.

Not called during doc generation (it would change the demo request); the agent's call is `vault_append(path=<request>, content="\n\n---\n**Агент (...):** <status> → [[Плани/...]]")`.

## Failure behaviour (what the defence demonstrates)

| Failure | What the agent prints | Effect |
|---|---|---|
| Obsidian closed / plugin off | `Obsidian MCP is not reachable at https://127.0.0.1:27124/mcp/. Is Obsidian open ...?` | stops before any change |
| Wrong `OBSIDIAN_API_KEY` | `obsidian rejected the credentials (HTTP 401). Check OBSIDIAN_API_KEY in .env.` | stops before any change |
| Request note missing | `Запит не знайдено в Obsidian (File not found: ...). Наявні запити: ...` | stops; lists existing requests via vault_list |
| Obsidian lost before the final write | `Obsidian недоступний при записі ... План збережено локально: out/...` | plan kept locally |

Raw tool result for a missing note:

```json
{
  "isError": true,
  "text": "File not found: Запити/Неіснуючий запит.md"
}
```
